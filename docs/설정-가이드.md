# argusDesk 설정 가이드

설정은 YAML 한 벌입니다. 어떤 Jira 프로젝트를 어느 층에 보여줄지, 상태가 어느 방에 해당하는지, 유형마다 송장 색과 묵은 상자 기준이 무엇인지를 정합니다. 이 문서의 이름과 ID는 모두 가짜이고, 형식은 `config/example.yaml`과 같습니다.

실제 설정에는 사내 Jira의 유형, 상태, 승인 단계가 들어가므로 저장소에 올리지 않습니다.

## 설정을 고치고 배포하는 방법

팀 서버(Argus)를 쓰는 경우와 파일을 쓰는 경우가 다릅니다.

| | 팀 서버 | 파일 |
|---|---|---|
| 고치는 곳 | 설정 YAML을 고쳐 Argus 관리 화면(ArgusDesk 연동 › 설정 배포)에 올림 | 각자 컴퓨터의 YAML 파일 |
| 앱에 반영 | 5분 안에 자동. 바로 받으려면 내 상태 › "서버에서 설정 다시 받기" | 내 상태 › "설정 다시 읽기" |
| 되돌리기 | 관리 화면의 이력에서 이전 버전을 다시 적용 | 파일을 되돌림 |
| 화면 왼쪽 위의 버전 | 서버가 매긴 버전(`v3`) | 파일의 `version` |

설정에 문제가 있으면 앱은 문제를 한꺼번에 모두 알려 주고, 직전에 쓰던 설정으로 계속 돕니다. 오타가 난 키(`statuz_zones`)도 오류로 잡습니다.

## 맨 위 항목

```yaml
version: "2026-11-25.1" # 파일을 고칠 때마다 올립니다
name: 요청 센터
site: example.atlassian.net
timezone: Asia/Seoul    # 날짜만 있는 필드를 읽는 시간대 (기본 Asia/Seoul)
poll_seconds: 60        # Jira를 다시 읽는 간격. 15초보다 짧게 둘 수 없음 (기본 60)
```

## 공간(`spaces`): 보드 하나가 한 층

공간 하나는 Jira 프로젝트 하나이고, 건물의 한 층으로 보입니다. 적힌 순서대로 1층, 2층이 됩니다.

```yaml
spaces:
  - id: requests        # 앱 안에서 쓰는 이름. 영문, 겹치면 안 됨
    name: 요청 센터      # 화면에 보이는 이름
    project: REQ        # Jira 프로젝트 키
    create: true        # 선택: 팀이 직접 티켓을 만드는 프로젝트
    attach: true        # 선택: 티켓에 파일을 붙일 수 있음
    zones: [...]
    status_zones: {...}
    workflows: {...}
    types: {...}
```

| 항목 | 뜻 |
|---|---|
| `create` | 켜면 그 층 대기 구역의 접수대가 송장 작성대가 되고, 누르면 티켓을 만드는 송장이 열립니다. 송장의 입력 항목은 Jira의 생성 화면에서 그대로 읽어 옵니다. 끄면 받기만 하는 층입니다. |
| `attach` | 켜면 티켓 창에서 파일을 올리고 첨부 목록을 볼 수 있습니다. `create`도 켜져 있으면 송장에 파일을 담아 같이 보낼 수 있습니다. |
| `jql` | 선택. 앱이 만드는 조회 조건 대신 쓸 JQL. 보통은 필요 없습니다. |

앱은 `types`에 적힌 유형의 열린 티켓만 읽습니다. 프로젝트에 다른 팀의 유형이 섞여 있어도 적지 않은 유형은 화면에 나오지 않습니다.

### 구역(`zones`): 방

구역은 적힌 순서대로 놓입니다. 한 줄에 세 개씩이고, 둘째 줄은 오른쪽에서 왼쪽으로 놓여 컨베이어가 한 바퀴 돕니다.

```yaml
zones:
  - { id: lobby, name: 접수 로비, kind: wait }
  - { id: review, name: 검토실, kind: work, stale: { after: 3h, from: zone_entered } }
  - { id: work, name: 작업장, kind: desk, stale: { after: 5d, from: type_field } }
  - { id: dock, name: 출고 도크, kind: done }
  - { id: returns, name: 반송함, kind: returned }
```

| `kind` | 쓰임 |
|---|---|
| `wait` | 팀 밖의 결정을 기다리는 곳, 또는 시작 전 대기 |
| `work` | 팀이 처리하는 곳(검토, 승인) |
| `desk` | 담당자별 책상이 놓이는 작업장. 층에 하나를 권합니다 |
| `done` | 완료. 1층이면 트럭이 싣고 떠납니다 |
| `returned` | 반려, 취소 |
| `siding` | 다른 팀의 승인을 기다리는 곳. 방이 아니라 컨베이어 옆 지선에 섭니다 |

그 밖의 항목은 이렇습니다.

- `stale`: 그 구역에서 상자가 묵었다고 보는 기준입니다. `after`는 `30m`, `3h`, `5d` 형식입니다. `from: zone_entered`는 구역에 들어온 때부터, `from: type_field`는 유형의 `stale_field` 날짜부터 셉니다.
- `approval: true`: 서비스 데스크 승인 기능이 아니라 상태 이동으로 승인하는 구역에 붙입니다. 승인 정보를 읽지 못했을 때 가능한 이동을 승인·반려로 보여 줍니다.

### 상태와 구역(`status_zones`)

Jira 상태 ID를 구역에 잇습니다. 이름은 Jira에서 바뀔 수 있으므로 ID로 적고 주석에 이름을 답니다.

```yaml
status_zones:
  "10001": lobby # 요청 부서 승인 대기
  "10002": review # 검토 중
```

상태 ID는 Jira에 로그인한 브라우저에서 `https://<사이트>/rest/api/3/project/<프로젝트 키>/statuses`를 열면 유형별로 이름과 함께 나옵니다. 여기 적지 않은 상태의 티켓은 "미분류 선반"에 놓이므로, 빠뜨린 상태가 있으면 화면에서 바로 보입니다.

### 워크플로우(`workflows`)

상태에서 상태로 가는 길입니다. **송장의 경로 칸을 그리는 데만** 씁니다. 실제로 옮길 수 있는지는 Jira가 알려 주는 전환 목록을 따르므로, 여기가 조금 틀려도 처리는 잘못되지 않습니다.

```yaml
workflows:
  standard:
    start: "10001"
    paths:
      "10001": ["10002"]
      "10002": ["10003", "10006"]
    from_any: ["10007"] # 어느 상태에서든 갈 수 있는 상태(취소)
```

여기 나오는 상태는 모두 `status_zones`에 있어야 합니다.

### 유형(`types`)

키는 Jira의 업무 유형 이름이고, **글자 하나까지 같아야** 합니다(띄어쓰기 포함).

```yaml
types:
  "[REQ] 스키마 변경":
    workflow: standard
    tag: green                      # 송장 띠 색
    stale_field: 작업 완료 요청일시   # 작업장에서 날짜를 세기 시작하는 필드
    unscheduled: { unless_checked: 배포 일정 확정, label: 일정 미정 }
    xp: 20                          # 선택: 끝냈을 때 경험치
```

- `tag`: `orange` `purple` `blue` `green` `teal` `pink` `yellow` `navy` `gray` 중 하나.
- `stale_field`: `created`, `duedate`, 또는 사용자 정의 필드의 이름.
- `unscheduled`: 적힌 체크박스가 꺼져 있거나 날짜가 없으면 묵은 상자로 세지 않고 `label`을 붙입니다.

## 보드(프로젝트)를 추가하는 순서

코드를 고칠 필요는 없고 설정에 공간 하나를 더하면 됩니다.

1. **유형 고르기**: 새 프로젝트에서 팀이 볼 업무 유형의 이름을 그대로 적어 둡니다.
2. **상태 모으기**: 위의 `…/project/<키>/statuses` 주소에서 그 유형들의 상태 ID와 이름을 모읍니다.
3. **방 정하기**: 상태를 대기, 처리, 작업장, 완료, 취소로 묶어 `zones`를 만듭니다. 여섯 개 안팎이 보기 좋습니다.
4. **잇기**: `status_zones`에 상태 ID마다 구역을 적습니다.
5. **경로 적기**: Jira 워크플로우 그림을 보고 `workflows`를 적습니다. 급하면 `start`만 적어도 됩니다.
6. **유형 적기**: `types`에 유형마다 워크플로우와 색을 적습니다.
7. **성격 정하기**: 팀이 직접 만드는 프로젝트면 `create: true`, 파일을 붙일 거면 `attach: true`.
8. **버전 올리고 배포**: `version`을 올리고 팀 서버에 올리거나 파일을 바꿉니다.
9. **확인**: 새 층에 "미분류 선반"이 생기면 빠진 상태가 있는 것입니다. 송장을 쓰는 층이면 유형마다 송장을 열어 입력 항목이 Jira 생성 화면과 같은지 봅니다.

화면 없이 배치만 글자로 확인하려면 아래 명령을 씁니다.

```sh
ARGUSDESK_TOKEN=<API 토큰> go run ./cmd/argusdesk-dump -config <설정 파일> -email <Jira 이메일>
```

알아 둘 것이 있습니다.

- 각 사용자의 Jira 계정에 그 프로젝트를 볼 권한이 있어야 합니다. 권한이 없는 사람의 앱은 그 층의 티켓을 읽지 못합니다.
- 송장으로 티켓을 만들려면 그 유형의 생성 화면에 있는 필수 항목을 앱이 채울 수 있어야 합니다. 채울 수 없는 필수 항목(자산 선택 등)이 있으면 송장이 "Jira에서 만들기"로 안내합니다.
- 유형을 빼면 그 유형의 티켓은 화면에서 사라지고 송장의 유형 목록에서도 빠집니다.

## 그 밖의 선택 항목

```yaml
game:
  season_start: "2026-01-01" # 경험치를 세기 시작하는 날 (기본: 올해 1월 1일)
  xp: 10                     # 끝낸 티켓 하나의 경험치
  tired: 25                  # 한 주에 끝낸 작업이 이 수를 넘으면 아바타가 피곤해 보임
  exhausted: 35              # 이 수에 이르면 피로도가 0: 상자를 더 가져올 수 없음 (월요일에 초기화)

vacation:
  kinds:                     # 연차, 오전반차, 오후반차는 기본. 여기에 팀의 것을 더함
    - { name: "리프레시" }
    - { name: "오전반반차", half: true } # half: 하루 중 일부만 쉼. 하루만 등록, 아바타는 센터에 남음

team:
  state_issue: REQ-1 # 팀 서버 없이 휴가를 서로 보려면: 모두가 수정할 수 있는 티켓
```

휴가 구분의 이름은 팀 캘린더 일정 제목(`이름 / 구분 / 대무자 : 이름`)에 그대로 들어갑니다.

## 개인 설정은 여기에 없습니다

아바타, 알림, 단축키는 설정 파일이 아니라 앱의 내 상태에서 각자 정합니다. 단축키는 내 상태 › "단축키 설정"에서 바꿉니다.
